## Intent

**`cmd-session.sh` — `session check`.** One verb, six deterministic checks plus two print-only advisories, over the close of a session. The module header (`:9-16`) states what it deliberately does *not* do — bookkeeping (unlisted files, stale views, record drift) and prescribing a governance command — because "four of six acceptance runs died on that class and prevented nothing." `res()` (`:27-34`) is a thin adapter onto `lib/cli.sh`'s row vocabulary: PASS→`row_pass`, FAIL→`row_fail`, anything else→`row_warn`, and always `return 0` so emitting a row can never itself fail the function (this is P-01's mechanism, reused here rather than reimplemented).

`CLAIMED` (`:57`) is deliberately scoped to `in_review` tasks plus tasks accepted *today* — not "everything touched today" (a metadata-only edit is not work done, `:47-50`) and not every historical acceptance (`:51-54`, which would fail an old repo forever over receipts predating the receipt field). This is the set the session is answerable for.

Six checks, in order:
1. **Receipt present** (`:59-77`) — every claimed task has a receipt, and it is green (`rc == 0`).
2. **Command match** (`:79-93`) — the receipt's `.receipt.command` equals the order's `.task_order.verification_command`; catches a verify run against something easier than what was ordered.
3. **Receipt fresh** (`:95-126`) — no file the receipt covers has an mtime after `.receipt.at_epoch`. `COVERED` reads **both** `task_order.context.files` and `task_order.context.expected_artifacts` (`:111`); the inline comment at `:103-110` documents that this used to read only `context.files` because `expected_artifacts` was mis-read at the top level of `task_order` instead of nested under `context` — a shipped bug, now fixed, kept as commentary rather than scrubbed. Compares against `WORK_ROOT`, not `ROOT` (`:113-114`) — code lives in the worktree, records live on main.
4. **Checks ran** (`:128-141`) — `.receipt.checks_run != 0`; a verify that narrowed to zero checks and reported green is "the most dangerous green there is."
5. **Strays/secrets** (`:143-165`) — greps `git status --porcelain` in `WORK_ROOT` for temp/secret-shaped paths. Gated on `git -C "$WORK_ROOT" rev-parse --git-dir` (`:156`), not `[ -d "$WORK_ROOT/.git" ]` — the inline comment (`:146-155`) is PK-3's own fix note: in a git *worktree* `.git` is a **file**, so the old directory test silently turned off the one irreversible check in the close (a committed secret) in exactly the configuration D-0084's parallel dispatch builds by design.
6. **Nothing mid-flight** (`:167-197`) — no task left `in_progress`. D-0084-aware: with `SCRUMUX_TASK` set (the app's own dispatch id), *this session's* in-flight task FAILs and any other in-flight task is named as a WARN (`:184-193`); with no `SCRUMUX_TASK` (a hand session) it reverts to the old all-or-nothing FAIL (`:194-196`).

Two prints that never move the exit code (`:199-244`): sprint discipline (worked outside a ratified sprint) and live stub markers cross-checked against `issues.json` status. Verdict (`:246-253`) is `cli_fails()`/`cli_rows()` over the row set the six checks fed — the "clean" line even says push is User's call, not the close's.

**`cmd-sprint.sh` — `sprint {new,add,update,descope,ratify,status}`.** `new` (`:6-58`) opens either an epic-bounded sprint or a `--hotfix --issue` fast lane; the two are mutually exclusive (`:33`). The hotfix lane runs exactly one task, so `--parallel` other than 1 is refused rather than silently overridden (`:28-29`) — "a cap the operator asked for and did not get is the kind of quiet disagreement this CLI exists to stop." A hotfix issue must be `reproduced`/`evidenced`-validated or User-authorized (`:36-45`); `invalidated` and `duplicate` states each get their own refusal naming the fix.

`add` (`:59-82`) requires the task to already have a `task_order` (D-0005) and, unless the sprint is a hotfix or the order is `light` (T-0189/D-0073, `:67-74`), requires a `story`. `descope` (`:83-120`) requires `--reason` (`:96-97`, with a GOOD/BAD example baked into the refusal text) and, when the task carries log entries, prints a `TELL` and **performs the descope anyway** (`:104-113`) rather than refusing — T-0144 converted this from a block because "the old message already named both alternatives... and refused to do it anyway."

`update` (`:121-148`) is the **one** field editable post-creation (`--parallel`), and only while the sprint is still `proposed` (`:144-145`) — changing admission width on a ratified plan is "a re-ratification, not an edit."

`ratify` (`:149-176`) requires both `--by` (`:166`) and `--authority` (`:167`, via `authority_guard`). The inline comment (`:151-158`) states the removed default explicitly: `--by` used to default to the literal `User`, which "wrote his name onto acts he did not take," with nothing in the CLI verifying who is actually calling (same P-21 principle).

**`cmd-repair.sh` — `repair journal <name> --apply <jq> --why --by`.** The sanctioned hand-correction path, single verb (`repair_run:106-115` refuses anything but `journal`). All three of `--apply`/`--why`/`--by` are required (`:23-32`); the `--by` refusal text names the same "defaulted to User" defect as `sprint ratify`'s. Sequence, and the sequence is load-bearing:

1. `BEFORE=$(seal_of "$GOV/$JF")` (`:34`) — hash before anything happens.
2. **Dry run** (`:42-54`): `jq "$EXPR"` into a temp file, with stderr captured separately (`_chkerr`) and its **first line** relayed in the refusal (`:49-52`) — this is OQ-13, already resolved in this tree's bash (the inline comment at `:43-47` cites "D-0085/OQ-13" directly and explains why: `2>/dev/null` used to discard jq's own syntax-error diagnostic and refuse with only "check the filter"). **Caveat:** `docs/port/PHILOSOPHY.md`'s own OQ-13 write-up (its "Open Questions" section, `:1745-1765`) still describes the pre-fix `2>/dev/null` behavior and has not been updated to say so — the source and the register have drifted apart on this one entry; see Open Questions below.
3. Empty-output guard (`:55`) and no-op guard (`:56-57`, comparing `seal_of` of the dry-run output against `BEFORE`) — both die *before* any write, which is the ordering fix the comment at `:35-41` explains: `write_json` now reseals the file it writes, so if the no-op check ran *after* the write, a repair on an already-tampered journal would rewrite the same bytes, reseal them, and erase the tamper evidence with no record. "That is a hole, not a cosmetic ordering problem."
4. `write_json "$GOV/$JF" "$EXPR"` (`:58`) — **re-runs the filter** against the real file (OQ-14: the filter therefore executes twice, once for the dry-run hash and once for the real write). `write_json` carries its own independent guards inherited from `lib.sh` (`_write_json_body`) that `repair_impl` does not duplicate: the produced JSON must be an object with an `entries` array (`lib.sh:206-208`), and a write that *reduces* the entry count is refused unless `ALLOW_ENTRY_REMOVAL=1` is set in the environment (`lib.sh:220-232`) — `repair_impl` does not set this itself, so an `--apply` filter that drops entries dies inside `write_json`, **after** the repair's own no-op/empty-output guards passed, and **before** the log entry is written. No partial state: if `write_json` dies, nothing about the repair (including its log entry) has happened yet.
5. `log_new` (`:59-63`) — the log entry and the write are documented as one operation (T-0100): "the record cannot be forgotten." `log_new` is called with no `--task`, so the task-linking half of `log_new` (`cmd-log.sh:19,29-30`) never fires for a repair.
6. `seal_bootstrap; say` (`:64-65`).
7. **Machinery check** (`:67-89`), only when `$ROOT/.claude/DEPLOYED` exists and `$SCRIPTS/scrumux` is executable (`:83`): runs `harness verify`, never `harness deploy` (`:72-77` explains why — deploy fails the whole install on any record finding, dragging record hygiene into a path where it does not belong, boundary 7), and its result is printed as `say`/`TELL` and **never changes repair's own exit code** (`:80-82`) — "the records are already corrected, and a drifted machinery file is not a reason to make that look like it failed." This is P-51.

## Deliberate looseness

- **Advisory rows never move the exit code** (`session_check`'s `res()` WARN branch, sprint-discipline and live-stub prints, T-0144's descope-with-a-worked-task TELL) — **P-01**, and the specific rows "worked outside a ratified sprint" and "stale STUB marker" are named row-by-row in **P-06**'s table.
- **`session check` deliberately does not check bookkeeping** — unlisted files, stale views, record drift (`cmd-session.sh:9-14`) — consistent with **P-06**'s boundary-7 principle (record hygiene is User-inspection data, never an agent block) though this module's own header states it independently rather than citing a P-number; no exact PHILOSOPHY.md entry names `session check`'s header directly, so treat it as an application of P-06 rather than a new item.
- **A live stub marker WARNs, never FAILs** (`cmd-session.sh:239-244`) — **P-05** (the stub-and-park lane is sanctioned; a verify/close that passes over a marked stub is the lane working), applied here at the close rather than at `task verify`.
- **`sprint descope` performs the descope and only TELLs when the task was worked** (`cmd-sprint.sh:104-113`) — this is the exact T-0144 demotion **P-06** documents in its "eleven gates" table, row "`sprint descope` — task already has log entries."
- **`sprint ratify` requires `--by` and `--authority`, with no identity verification behind either** — **PK-5** (RULINGS.md D-0085) fixed the missing-flag half; the "does not check WHO is calling" half is **P-21**'s general principle, reused verbatim in this noun (`authority_guard` is shared machinery, not reimplemented per-noun — see `lib.sh:437-439`'s own statement of the limit).
- **`authority_guard` accepts bare `app` (no `:<session>`) as well as `app:<session>`** (`lib.sh:456-457`) — narrower than it looks at first read but is commented as deliberate: a sprint ratification is repo-level and belongs to no dispatch session, so writing an invented `app:unknown-session` would be the same fabrication P-08/P-21 warn against elsewhere. No PHILOSOPHY.md item names this specific branch; flagged **NEW** (candidate) since it is a permissive parsing case a porter could plausibly "tighten" into requiring a session id always.
- **`session check`'s worktree gate asks git, not the filesystem** (`cmd-session.sh:156`) — **PK-3** (RULINGS.md D-0085), already applied in this tree.
- **`repair journal`'s stderr relay** (`cmd-repair.sh:49-52`) — **OQ-13**, resolved per RULINGS.md D-0085; PHILOSOPHY.md's own Open-Questions writeup of OQ-13 has not been updated to match (see Open Questions below).
- **`repair journal` executes its `--apply` filter twice** (dry-run hash, then the real write inside `write_json`) — **OQ-14**; RULINGS.md D-0085 already approves a TS divergence (write the already-checked bytes once) under `// APPROVED-DIVERGENCE: D-0085`. Current bash still runs it twice; see Simplify/perf.
- **`repair journal`'s machinery check never changes the repair's exit code, and only runs in a deployed repo** — **P-51**, verbatim.
- **A repair that would reduce a journal's entry count dies inside `write_json`'s shared guard, not inside `repair_impl`'s own checks**, and `repair_impl` never sets `ALLOW_ENTRY_REMOVAL` — this is the entry-count-reduction guard described generally in PHILOSOPHY.md's write-path discussion (Group B, around P-09/P-13's neighborhood) but there is no P-number naming `write_json`'s `ALLOW_ENTRY_REMOVAL` guard itself or its interaction with `repair`. Flagged **NEW** (candidate): the register should record that `repair`'s only way to *intentionally* shrink a journal is the caller setting an environment variable the command's own `--help` never mentions.
- **`sprint new --hotfix` refuses a non-1 `--parallel` rather than silently forcing it to 1** (`cmd-sprint.sh:28-29`) — no PHILOSOPHY.md item names this specific refusal; it is the same "an allow rule wins, a conf wins, a wall does not argue with its owner but also does not silently override a stated preference" ethos as **P-29**'s neighborhood, but not a direct instance. Flagged **NEW** (candidate).
- **`sprint update`'s re-ratification refusal on anything but `proposed`** (`cmd-sprint.sh:144-145`) — no direct P-number; same family as P-06's demotions but in the opposite direction (this one stayed a hard refusal, not a TELL) precisely because it changes what User already ratified. Flagged **NEW** (candidate) — worth registering explicitly since a porter used to seeing every other gate in this file demoted to TELL could plausibly "finish the pattern" here and weaken a refusal that was deliberately kept strict.
- **`session check`'s unstamped-receipt case WARNs rather than PASSing or FAILing** (`cmd-session.sh:122-123`, `.receipt.at_epoch` absent) — a tri-state read of a boolean-shaped question ("is it fresh"), same spirit as **P-16**'s tri-state principle but not itself a PHILOSOPHY.md entry. Flagged **NEW** (candidate).

## Simplify/perf

- **BEHAVIOR-PRESERVING** — `session_check`'s stub scan (`cmd-session.sh:220-222`) shells out to `find` + a `while read` loop + `grep -onE` per file; this can become a single in-process directory walk plus one regex pass per file read once, with identical prune list (`.git`, `governance`, `tests`, `node_modules`, `.venv`, `venv`, `dist`, `build`) and identical exclusion of `AI_LOG.MD`/`DECISIONS.MD`/`BACKLOG.MD`. No subprocess `find`/`grep` needed in TS.
- **BEHAVIOR-PRESERVING** — every `jget "$TASKS" ...` call in `session_check` (six of them, one per check) re-parses `tasks.json` from disk. One parse of `tasks.json` and one of `sprints.json` per `session check` invocation, held in memory across the six checks, changes no observable output.
- **BEHAVIOR-PRESERVING** — `mtime_of()` (`cmd-session.sh:37-39`) shells to `stat` twice (BSD then GNU flag) per file; TS gets this from `fs.statSync(...).mtimeMs` directly, no subprocess.
- **BEHAVIOR-PRESERVING** — `repair_impl`'s dry-run + real-write double `jq` invocation (OQ-14) collapses to one filter evaluation whose output is both hashed (for the no-op/empty-output checks) and written, **per the already-approved D-0085 divergence** — this is not a new proposal, it is executing a ruling already on the books; the TS site must carry `// APPROVED-DIVERGENCE: D-0085`. Preserve the *order* of checks (empty-output guard, then no-op guard, then the shape/entry-count guards `write_json` would otherwise apply) even though they now run against one evaluation instead of two.
- **BEHAVIOR-PRESERVING** — `sprint_impl`'s repeated `jq -r --arg ...` single-field reads (e.g. `VSTATE`, `AUTHED` in the hotfix branch, `HOT`/`LIT` in `add`) can become one parse of the relevant journal per verb invocation with field access in-process; the refusal conditions and messages are unchanged.
- **OBSERVABLE** — none identified in this module that would change what an operator sees. Every behavior above is reproducible byte-for-byte in the exit code, row text and refusal text; the changes are all execution-strategy (fewer subprocesses, fewer re-parses), not new checks or relaxed ones. If a proposal along these lines is later found to shift a message or a code path, it belongs in this section as OBSERVABLE and needs a ruling — none is proposed here.

## Open questions

- **PHILOSOPHY.md's OQ-13 entry is stale against the current bash.** `docs/port/PHILOSOPHY.md:1745-1765` still describes `cmd-repair.sh:43` as `2>/dev/null`, discarding jq's diagnostic. The tree at this inspection (`cmd-repair.sh:42-54`) already captures stderr into `_chkerr` and relays its first line, with an inline comment explicitly citing "D-0085/OQ-13." RULINGS.md confirms this was fixed in the Phase 1a bash-first window. The register itself was not updated to mark OQ-13 resolved. Not a code hazard — a documentation-drift hazard: a later reader of PHILOSOPHY.md alone would believe OQ-13 is still open and could "fix" already-fixed behavior, or misjudge what "port as-is" means at that site.
- **`ALLOW_ENTRY_REMOVAL` is an environment variable with no `repair` flag surfacing it** (`lib.sh:220-232`, consumed silently by `write_json` inside `repair_impl`'s call at `cmd-repair.sh:58`). TS-port hazard: if the TS CLI's process/env model differs from a POSIX shell's (e.g., a long-running daemon dispatching multiple `repair` calls rather than one process per invocation), this env-var gate needs an explicit carrier — passing it through `process.env` per-call, or an equivalent — or an intentional shrink via `repair journal --apply` becomes unreachable in the port where it was reachable in bash. `cmd-repair.sh:20-32,58`; `lib.sh:220-232`.
- **`sprint descope`'s TELL is computed from `log.json`, and only when `governance/log.json` exists** (`cmd-sprint.sh:104` — `if [ -f "$GOV/log.json" ]`). A repo whose `log.json` has never been written (a fresh deploy, per P-38/P-19's "empty registry" pattern) silently skips the TELL, even for a task with real prior work recorded some other way — though in practice `log.json`'s absence and "this task was never logged" should coincide. Worth confirming in the port that "no log.json" and "zero matching log entries" are treated identically (both currently produce silence, no TELL) rather than one becoming an error.
- **POSIX ERE vs JS RegExp, sort/locale — not exercised in this module.** Unlike the walls (`block-*.sh`) or `walls-lib.sh`, none of these three files compile a regex from external/conf-file input; the only pattern matching is the fixed `grep -E '\.tmp\.|\.env$|id_rsa|\.pem$|\.key$'` in `session_check`'s stray scan (`cmd-session.sh:157`), which is a small, static ERE with no anchoring ambiguity between POSIX ERE and JS RegExp (no POSIX bracket classes, no BRE-only backreferences). Low hazard; still worth a literal port (not a "cleaner" `/\.(tmp\.|env)$|id_rsa|pem$|key$/` rewrite) so the exact match set is provably unchanged.
- **Subshell exit-code swallowing: `STUBSCAN=$(cd "$WORK_ROOT" && find ... | while IFS= read -r f; do grep ...; done)`** (`cmd-session.sh:220-222`). The `while` loop's exit status is not checked, and neither is `find`'s or `grep`'s (each `grep -onE ... 2>/dev/null` can legitimately exit 1 on no match, which is expected and already tolerated) — but a `find` permission error partway through a large tree would print to stderr (unredirected) and continue, silently omitting whatever subtree it could not read, with no signal in the check's PASS/WARN output that the scan was partial. Not verified as deliberate (no comment addresses it); port note: reproduce the "partial scan reports as if complete" behavior rather than adding a completeness check, per the no-silent-tightening rule — but flag it here since it is exactly the kind of gap a porter's instinct is to close.
- **`printf` format edges: none identified.** No `printf %d`/`%x`/width-specifier usage in these three files beyond `printf '%.12s'` (`cmd-repair.sh:61`, truncating the seal hash for the log message) and `printf '%s\n'` — both are plain-string operations with no numeric-format ambiguity between `sh`'s `printf` and a JS template-string equivalent.
- **`sprint new`'s `--parallel` default is recorded as an explicit `1`, not `null`** (`cmd-sprint.sh:53`, `--argjson p "${PARALLEL:-1}"` — confirmed by `tests/scrumux-tests.sh:966`, "a sprint opened with no `--parallel` must record `parallel:1` EXPLICITLY, never null"). Straightforward to port, flagged only because a default baked into a `jq --argjson` fallback is an easy place for a TS rewrite to instead leave the field `undefined`/omitted, which is an observable schema difference under `--json`.
